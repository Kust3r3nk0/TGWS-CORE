# Техническое задание — TGWS-CORE

**Идентификатор:** TZ-CORE-001  
**Версия документа:** 1.0-draft  
**Дата:** 2026-10-30  
**Репозиторий:** https://github.com/Kust3r3nk0/TGWS-CORE  
**Приложения-потребители:** https://github.com/Kust3r3nk0/TGWS-CLODEX  
**Статус:** планирование; отсутствуют реализованное ядро, опубликованный ABI и подтверждённая производительность.

## 1. Цель проекта

Создать **общее переносимое ядро локального MTProto/WebSocket-прокси** для нативных мобильных приложений Android и iOS. За основу поведения берётся оригинальный [TG WS Proxy от Flowseal](https://github.com/Flowseal/tg-ws-proxy), но реализация TGWS-CORE разрабатывается **с нуля**, а не путём копирования старого TGWS-Android.

Референс изучен на коммите [307a384ab7f522e34bb1a045884d0bd90f40bee5](https://github.com/Flowseal/tg-ws-proxy/commit/307a384ab7f522e34bb1a045884d0bd90f40bee5) (2026-10-30); при изменениях upstream требуется отдельное ревью совместимости.

**Правило разделения:** ядро не содержит Android/SwiftUI, разрешений ОС, экранов, lifecycle foreground service, политик App Store и Telegram SDK; эти задачи принадлежат TGWS-CLODEX.

## 2. Источник поведения и границы совместимости

Оригинальный upstream реализован преимущественно на Python и включает: локальный MTProto listener (по умолчанию 127.0.0.1:1443), разбор obfuscation init и определения Telegram DC, перенаправление через WebSocket/TLS, механизм fallback на Cloudflare Proxy/Worker и прямой TCP, варианты Fake TLS и HTTP/2, обработку медиа, управление пулами соединений и диагностические данные. Наличие функции в upstream **не означает**, что она включена в TGWS-CORE MVP.

### 2.1 План профилей совместимости

| Профиль | Приоритет | Содержание |
| --- | --- | --- |
| BASE | P0 | MTProto handshake и frame/stream framing, выбор DC, TLS/WebSocket, корректная двунаправленная передача, безопасный локальный listener |
| RESILIENCE | P0/P1 | Контролируемое переподключение, deadline/timeout, надёжное закрытие, повторяемые ошибки; direct TCP fallback после явного задания политики |
| CF | P1 | Плагины Cloudflare Worker и/или CfProxy и правила маршрутизации после проверки угроз и внешних зависимостей |
| MEDIA | P1 | Проверяемая совместимость с media DC, передача больших файлов без unbounded buffer, тесты фото/видео |
| ADVANCED | P2 | Fake TLS, HTTP/2, domain balancing и расширенные режимы upstream после отдельного ADR |

**Запрещено:** маркировать неподдерживаемый транспорт как «доступный», включать непроверенный fallback молча или имитировать поддержку иными API.

## 3. Архитектура и модульные границы

~~~text
TGWS-CORE
  public API / ABI boundary
       │
  runtime supervisor + state machine + config validator
       │
  local MTProto listener (loopback)
       │
  MTProto protocol parser / relay transform / DC router
       │
  transport policy + health / backoff / connection pool
       ├── WebSocket over TLS [P0]
       ├── Direct TCP fallback [P1 after security-policy review]
       ├── CF Worker / CF Proxy [P1]
       └── HTTP/2 / Fake TLS options [P2]
       │
  error model + structured events + test harness
~~~

Предлагаемый язык: **Rust** с асинхронным runtime (например, Tokio), тестами cargo, библиотекой для Android и статическим артефактом/поддерживаемой упаковкой для iOS. Это **проектное предложение**, не формально выбранная реализация. Архитектура должна допускать change-of-language до утверждения ADR; прикладной API не должен зависеть от конкретного рантайма.

### 3.1 Целевая структура репозитория (после подтверждения ADR)

~~~text
TGWS-CORE/
  crates/
    tgws-protocol/       # MTProto parsing, DC selection, test vectors
    tgws-transport/      # WS/TLS, fallback interfaces, timeouts
    tgws-runtime/        # listener, sessions, connection pools, state
    tgws-api/            # versioned API and FFI boundary
    tgws-diagnostics/    # sanitized events / metrics
  tests/
    fixtures/            # безопасные фиксированные протокольные данные
    integration/
    fault-injection/
  bindings/
    android/
    ios/
  docs/
    TECHNICAL_SPECIFICATION.md
    INTEGRATION_CONTRACT.md
    adr/
  .github/workflows/
  README.md
~~~

Приведённые пути — **план структуры**; существующие папки не предполагаются. Реализация должна избегать циклических зависимостей, отдельной логики MTProto в каждом клиенте и смешивания transport/GUI.

## 5. Модель состояния и жизненный цикл

~~~text
CREATED -> STARTING -> RUNNING -> STOPPING -> STOPPED
               │          │          │
               └-----> ERROR <-------┘
                          │
                        STOPPED

Внутри RUNNING возможно событие TRANSPORT_DEGRADED/RECONNECTING;
локальный listener и доступность upstream НЕ эквивалентны.
~~~

- **CREATED:** конфигурация прошла локальную проверку, сокеты не открыты.
- **STARTING:** попытка bind и инициализация runtime.
- **RUNNING:** listener подтверждён и принимает соединения; это **не доказательство**, что Telegram DC доступен.
- **RECONNECTING/TRANSPORT_DEGRADED:** диагностическое событие сетевой сессии, а не обязательный отказ listener.
- **STOPPING:** запрет новых подключений, graceful shutdown, затем принудительный deadline.
- **STOPPED:** все ресурсы освобождены, порт закрыт.
- **ERROR:** системная ошибка с кодом, контролируемой очисткой и возможностью безопасного перезапуска.

Операции запуска/остановки идемпотентны; параллельные операции сериализуются. Нельзя возвращать «успешно» до завершения реального bind. Коллекции tasks/streams не растут без предела.

## 6. Сетевая спецификация и policy engine

### 6.1 Listener

- По умолчанию 127.0.0.1 и port 1443; другие локальные порты разрешены после validation.
- Привязка к 0.0.0.0, публичному адресу и интерфейсу Wi-Fi запрещена по умолчанию. Расширение периметра — отдельный threat model/ADR.
- Требования к IPv6 loopback (::1) оформляются отдельно после проверки поддержки Telegram и ОС.
- Отказ при bind и повторное занятие порта должны возвращать различимые ошибки.

### 6.2 MTProto и upstream parity

- Поддерживать релевантные разновидности obfuscated MTProto transport и защищённую обработку init-пакета в соответствии с проверенными upstream test vectors.
- Корректно определять Telegram DC, media/test DC при поддержке конфигурации; неизвестные значения отклонять без необработанных исключений.
- Корректно формировать и ретранслировать поток в модели, совместимой с upstream. Нельзя предполагать, что достаточно «просто WebSocket поверх TCP»: upstream использует разбор фреймов и преобразование контекстов потока.
- Для каждого протокольного решения требуются тесты положительных/отрицательных входов и задокументированная сверка с upstream.

### 6.3 WebSocket/TLS

- Реализация стандартного WebSocket handshake/фреймов, поддержка бинарных сообщений, continuation/close/ping-pong в объёме используемого транспорта.
- TLS с системными или явно доверенными корнями и обязательной проверкой hostname; запрет опций «игнорировать сертификат».
- Ограничения размера frame/message, чтения и записи; backpressure вместо неограниченного накопления.
- Передача DNS, системной сети и TLS ошибок с машиночитаемым кодом.
- Любые редиректы и новые домены проходят валидацию allowlist/policy; не допускать SSRF на локальные/частные сети при работе с удалёнными настройками.

### 6.4 Fallback и внешние сервисы

- Режимы и порядок попыток задаются конфигурацией; отсутствие CF не превращает прямой TCP в скрытое обязательное поведение.
- При direct TCP возможно изменение сетевой видимости соединения: UI должен раскрывать факт переключения через события/метрики; политика выбора согласуется с продуктом.
- CF Worker/CfProxy — опциональные upstream, которые могут быть недоступны, измениться или иметь ограничения. Никогда не требовать их для базового MVP.
- Exponential backoff с потолком и jitter; попытки для разных DC/адресов изолированы; отмена не создаёт искусственное состояние неисправности.

## 7. Конфигурация и интеграционный интерфейс

Детальный контракт — [docs/INTEGRATION_CONTRACT.md](./INTEGRATION_CONTRACT.md). Основные свойства:

- Версия конфигурационной схемы, версия runtime API и проверка совместимости до запуска.
- Конфигурация передаётся в память по явному действию приложения, не пишется ядром в небезопасный файл.
- Проверка диапазона порта 1..65535, формат secret, ограничения доменов, количество и размеры элементов списков.
- Запрещены неявное исполнение удалённой конфигурации, remote code loading и горячее внедрение транспортных модулей без контроля.
- Ядро не получает доступ к Keychain/Keystore напрямую: безопасное хранение и жизненный цикл секрета обеспечивают платформенные адаптеры.
- ABI не передаёт указатели на объекты внутренних Rust-структур; только opaque handles или стабильные value types.

## 8. Безопасность и угрозы

### 8.1 Цели безопасности

1. Ни одно удалённое соединение не может открыть локальный публичный listener.
2. Не допускаются buffer overrun, бесконтрольное использование памяти или паника на недоверенном handshake/frame.
3. Подмена TLS-сервера и доверие ложным сертификатам запрещены.
4. Секреты, ключевые материалы, пользовательские сообщения, адреса личных чатов и необработанные payload не попадают в логи.
5. Диагностические события не содержат raw secrets, ключей, IP клиентов, текстов чатов и query-параметров proxy deeplink.
6. Неиспользуемые соединения и ключевой материал очищаются насколько позволяет выбранная платформа; отсутствие копий plaintext в долговременном хранении проверяется.
7. Управление зависимостями, аудит CVE/OSV, lockfile и SBOM обязательны перед выпуском.
8. Все входы (handshake, frame, config, DC mapping, сетевые ошибки) считаются недоверенными и проходят строгую валидацию.

### 8.2 Threat-model минимум

- Соседнее приложение того же устройства пытается подключиться к localhost — проверка секрета и rate limits.
- Злонамеренный upstream, изменённый DNS, ложный сертификат, редирект на внутренний адрес.
- Неограниченный поток медиа, медленные соединения, клиентский DoS, многократный start/stop.
- Утечки из exception messages, crash dumps и логов диагностического экспорта.
- Race conditions на FFI callback и закрытии runtime из другой нити.
- Неожиданный переход Wi-Fi/cellular, sleep/wake, потеря сети и смена IP.

**Запрещено:** писать собственный криптоалгоритм или упрощать проверки совместимости «ради скорости»; использовать только прошедшие ревью криптобиблиотеки с тест-векторами.

## 10. Стратегия тестирования

### Unit и property-based

- MTProto obfuscation init, протокольные теги, media/test DC и невалидные DC.
- Splitter для abridged/intermediate/padded-вариантов, разрывы/слияния TCP chunks, граничные размеры.
- Конфиг: неизвестные поля, повторения, очень длинные значения, нестандартные порты, IP/private hosts.
- Модели ошибок и переходов состояния, проверки версии ABI.

### Integration / differential

- Локальный Telegram-клиент -> listener -> тестовый upstream -> обратный ответ.
- Проверяемые протокольные fixtures и дифференциальные тесты на выбранном upstream SHA.
- DNS timeout, сертификат истёк/подменён, WebSocket close, HTTP redirect, no route, connection refused.
- Исчерпание пула, slow consumer/producer, backpressure, half-close, отмена в разные моменты.
- Сеть Wi-Fi/cellular с объективными протоколами тестов на устройствах.

### Reliability и security

- 100 последовательных start/stop и 50 fault-recovery; рост RSS/FD после очистки не должен быть монотонным.
- Fuzz тесты handshake и WS frame parser с санитайзерами там, где поддерживаются.
- Dependency scanning, статический анализ, ABI smoke на arm64 Android и arm64 iOS.
- Test report хранит device/build, network context, версии upstream/core, результат и known issues.

## 11. Сборка, публикация ядра и совместимость

- Привязка к конкретным версиям компилятора, lockfile, воспроизводимые CI workflows и артефакты.
- Для Android ожидаются проверенные ARM64 (и эмуляторные ABI по потребности). Для iOS — архивы для симулятора и физического устройства, с учётом требований Apple к бинарным библиотекам.
- Артефакт версионируется через semver; ABI version проверяется при инициализации.
- Нельзя незаметно менять формат конфигурации, callbacks, ownership указателей и коды ошибок в минорной версии.
- Релиз сопровождается changelog, ссылкой на commit, checksum, test report и SBOM.
- Установочный процесс/CI не выполняет загрузку или запуск удалённых скриптов из непроверенных источников без закрепления версии и ревью.

## 12. Этапы, зависимости и критерии готовности

| Этап | Цель | Gate |
| --- | --- | --- |
| C0 — совместимость | Матрица функций upstream, зафиксированный SHA, fixtures, threat model | Каждая BASE-функция имеет сценарий проверки |
| C1 — базовое ядро | Listener, MTProto parser, WS/TLS, lifecycle | C-F01..C-F12 покрыты тестами и двумя мобильными smoke-клиентами |
| C2 — устойчивость | Fault injection, backpressure, cancellation, observability | C-N01..C-N10 подтверждены документами |
| C3 — расширения | CF/direct TCP/media по отдельным профилям | P1 прошли compatibility/security test |
| C4 — release core | Версии ABI, бинарные артефакты, SBOM, signing | Воспроизводимый CI и опубликованный отчёт |

### Definition of Done для core alpha

- [ ] Есть рабочий listener с MTProto handshake, DC selection и защищённым WS/TLS.
- [ ] Telegram выполняет реальный end-to-end smoke на Android и iOS согласно TGWS-CLODEX feasibility.
- [ ] Нет неограниченных очередей или известной необработанной panic на входных сетевых данных.
- [ ] Тестовые матрицы protocol, failure, memory, lifecycle доступны для воспроизведения.
- [ ] Прошла проверка сертификатов, безопасного bound address, секретов и логов.
- [ ] API/ABI контракт, threading и ownership документированы и проверены тестовым клиентом.
- [ ] Лицензионные уведомления фактически использованных upstream компонентов соблюдены.

## 13. Открытые архитектурные вопросы

2. Конкретный ABI: C headers, UniFFI/генерируемые bindings, версии Swift/Kotlin адаптеров.
3. Механизм локальной работы iOS, разрешения/энтитлменты и memory budget extension (если применимо).
4. Политика fallback: предпочтение безопасности/связности, условия переключения и прозрачность.
5. Лицензия нового ядра, third-party notices и способ сопровождения upstream.
6. Проверяемое поведение media DC и необходимость продвинутых транспортов.
